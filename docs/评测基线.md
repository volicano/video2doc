### 代码保真修复后的复测

2026-10-23 只改写作输入与后处理，不动 ASR，对两条基线分别从 write 阶段重跑：

| 指标 | BV1XKJR6xE5e 修复前 | BV1XKJR6xE5e 修复后 | BV1aWan6FEn9 修复前 | BV1aWan6FEn9 修复后 |
|---|---:|---:|---:|---:|
| OCR 代码画面 | 4 | 4 | 3 | 0 |
| 正文代码块 | 0 | 2 | 4（误报） | 0 |
| 质检里的代码问题 | 1 条 | 0 条 | 0 条 | 0 条 |
| 正文字数 | 2532 | 3633 | 4599 | 3763 |
| 未引用配图 | 4 | 4 | 4 | 4 |
| 代码与配图质量结论 | 代码缺失 | 代码可用 | 代码块是 OCR 噪声 | 不再生成噪声代码块 |

修复做了四件事：

1. 画面 OCR 不再一律压成一行：代码画面保留换行，并标成 `【代码画面】`；
2. 抽帧给代码画面保留名额，避免低分的代码截图被高分 UI 截图挤掉；
3. 写作提示要求输出围栏代码块；如果模型只写免责声明不写代码，按 OCR 里的 heredoc 抽一段代码补上；
4. 收紧「像代码」的判定：必须出现行首关键字（`const` / `def` / `import` / `await` …）、heredoc，或整帧多行真实代码，而不是括号多、出现 `=>` 就算代码。

复测里 BV1XKJR6xE5e 第 4 节能还原 `const task = await ...`、`openOrReuseTab(...)` 和 `snapshotText()`；BV1aWan6FEn9 不再把 Obsidian 的日历界面、日记模板、Tasks 示例当代码块。仍然存在的问题：OCR 符号会认错，heredoc 外层命令可能被一起抄进代码块，个别模型生成的代码块偏短；下一步要做多帧合并和代码清理。


### OCR 并行与检查点

2026-10-23 把 OCR 改成按帧并行（`ocr.workers = 4`，RapidOCR 的 ONNX 推理可共享实例），并把每帧结果写入 `cache/ocr_frames.json`：

| 指标 | 串行 | 4 线程 |
|---|---:|---:|
| OCR 耗时（26 帧） | 72.2s | 47.2s（1.53x） |
| OCR 文字 | 12,217 字 | 12,217 字 |
| 逐帧文本 / 置信度 | — | 完全一致 |

中途失败时，已完成的帧会保留；重新 `--from ocr` 只补未完成的帧。成功收尾后检查点自动删除。

ASR 也试过 faster-whisper 的 batched pipeline（`batch_size=8`，CPU）：236s vs 264s，只有 1.12x，文本相似度 96.7%。收益不足以承担默认行为变化，暂不启用。

## 发现

1. **时间戳和章节结构是稳的。** 两条都 0 错误、100% 覆盖、没有空节/短节/长节。这说明“模型只给句子编号、代码换算时间”的设计有效，后续优化不要动这条底线。
2. **配图有 19%–24% 没进正文，但还没到失控。** 26 张里 5 张、17 张里 4 张没被引用；`v2doc eval` 只在闲置比例超过 30%，或某一节有图却一张都没用时告警。真正要盯的是“某节有图但正文完全不引用”，而不是强迫模型把每张图都塞进去。
3. **代码检测收紧后，误报没了，真代码也留下了。** 原基线里 Obsidian 的 Dataview / Tasks 语法、浏览器视频的 Node.js 片段都被 OCR 读到了，正文却是 0 个代码块；第一版修复又反过来把 Obsidian 的日历界面、日记模板、Tasks 示例写成了代码块。现在用「行首关键字 / heredoc / 多行真实代码」判定：BV1XKJR6xE5e 仍识别出 4 个代码画面、正文 2 个代码块，BV1aWan6FEn9 的代码画面降到 0，不再输出噪声代码块。剩余问题是 OCR 符号错误、heredoc 外壳没剥掉、模型偶尔写短代码块，需要多帧合并和代码清理。
4. **速度瓶颈仍在 ASR。** OCR 并行后 26 帧从 72s 降到 47s（40 帧也从串行 ~122s 降到 ~78s），但 ASR 仍占 75% 以上，LLM 写作只占 5% 左右。CPU 上把 Whisper 改成 batched pipeline 只有 1.12x，收益不够；下一步要看 GPU / 云端或更小模型，而不是继续抠写作。
5. **图片体积有了可调参数。** 10 分钟、26 张图对应 1.2 MB 的单文件 HTML；现在可以用 `render.image_width` / `render.image_quality` 压到 900 KB 以下。对网页分享来说还能接受，但还缺默认压缩策略或响应式尺寸。
6. **旧任务的 LLM 用量缺失。** `job.json` 里 `usage` 为 0，但 write 阶段确实跑了 27s；这是早期版本没有记录用量，不是这次评测算错。评测会把它标成提示，不参与警告。

## 下一步

按收益排序：

1. 代码保真继续打磨：同一画面的多帧 OCR 合并、去掉 heredoc 外层命令、按语言清理符号和语言标注；模型漏写代码时保留兜底。
2. ASR 性能：CPU 上 batched pipeline 只有 1.12x，暂不默认；优先验证 GPU / 云端，或用更小模型配合术语表，目标把 10 分钟视频压到 5 分钟以内。
3. 图片默认压缩策略：评估 WebP 质量 / 响应式尺寸的默认组合，在清晰度和文件体积间取平衡。
4. 写作时优先引用已有配图；如果某节有图但正文完全不引用，自动重写或裁掉。
