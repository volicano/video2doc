2026-10-23 只改写作输入与后处理，不动 ASR，对两条基线分别从 write 阶段重跑：

修复做了四件事：

1. 画面 OCR 不再一律压成一行：代码画面保留换行，并标成 `【代码画面】`；
2. 抽帧给代码画面保留名额，避免低分的代码截图被高分 UI 截图挤掉；
3. 写作提示要求输出围栏代码块，并把清洗出的代码片段一起给模型；模型只写免责声明不写代码时，再按 OCR 的 heredoc 抽一段代码补上；
4. 收紧「像代码」的判定：必须出现行首关键字（`const` / `def` / `import` / `await` …）、heredoc、干净的多键 YAML 前置元数据，或整帧多行真实代码，而不是括号多、出现 `=>` 就算代码。URL、搜索结果里的重复键、半行 OCR 片段都会被排除。

复测里 BV1XKJR6xE5e 第 4 节能还原 `const task = await ...`、`openOrReuseTab(...)` 和 `snapshotText()`，并且不再把 heredoc 外壳抄进代码块；BV1aWan6FEn9 不再把 Obsidian 的日历界面、日记模板中的散文、Tasks 示例当代码块。仍然存在的问题：OCR 符号会认错，模型偶尔会省略代码块，个别模型生成的代码块偏短；下一步要做多帧合并和代码清理。

### ASR：GPU 与 large-v3-turbo

2026-10-23 用 BV1XKJR6xE5e 的 385.984s 音轨做同输入对比（`beam_size=5`、VAD；CPU int8 / GPU float16；相似度以原始 CPU `large-v3` 转写为参考，按归一化字符计算；模型已缓存，不含首次下载时间）：

| 配置 | 耗时 | 相对 CPU large-v3 | 字符相似度 | 说明 |
|---|---:|---:|---:|---|
| CPU `large-v3` | 260.1s（原 transcript 阶段） | 1.0x | 100% | 原始基线 |
| CPU `large-v3-turbo` + native hotwords | 95.6s | 2.7x | 96.5% | 产品名已纠正 |
| GPU `large-v3` | 64.9s | 4.0x | 98.9% | 质量最接近基线 |
| GPU `large-v3-turbo` + native hotwords | 15.5s | 16.8x | 97.1% | 推荐速度方案 |
| GPU `large-v3-turbo`，不加 native hotwords | 17.2s | 15.1x | 96.7% | EgoLite/EgoBrowser 会听成 eaglelite/eaglebrowser |

完整流水线也跑了一遍 GPU turbo（同一视频，6:26）：transcript 17.4s，整条流水线约 98s（含下载 9.3s、OCR 44.5s、写作 16.5s），成稿 3698 字、16 张图、`v2doc eval` 通过且 0 警告。

结论：

- GPU 已可用：RTX 5060 Ti + CTranslate2 4.8.3 + CUDA 12 运行库验证通过；CUDA 初始化失败会自动回退 CPU/int8。
- `large-v3` 仍保留为默认：GPU 上已有 4x，质量最接近原基线。
- `large-v3-turbo` 不设为默认：97.1% 相似度、分段更粗（40–68 段 vs 220 段），个别中文细节仍不如 `large-v3`；追求速度时配置 `model = "large-v3-turbo"`，并把产品名写进 `hotwords`。
- faster-whisper 1.2+ 的原生 `hotwords` 必须一起用：只加 `initial_prompt` 时 turbo 仍会把 EgoLite/EgoBrowser 听成 eaglelite/eaglebrowser。

## 发现

1. **时间戳和章节结构是稳的。** 两条都 0 错误、100% 覆盖、没有空节/短节/长节。这说明“模型只给句子编号、代码换算时间”的设计有效，后续优化不要动这条底线。
2. **配图有 19%–24% 没进正文，但还没到失控。** 26 张里 5 张、17 张里 4 张没被引用；`v2doc eval` 只在闲置比例超过 30%，或某一节有图却一张都没用时告警。真正要盯的是“某节有图但正文完全不引用”，而不是强迫模型把每张图都塞进去。
3. **代码检测收紧后，误报没了，真代码也留下了。** 原基线里 Obsidian 的 Dataview / Tasks 语法、浏览器视频的 Node.js 片段都被 OCR 读到了，正文却是 0 个代码块；第一版修复又反过来把 Obsidian 的日历界面、日记模板、Tasks 示例写成了代码块。现在用「行首关键字 / heredoc / 干净的多键 YAML / 多行真实代码」判定：BV1XKJR6xE5e 仍识别出 4 个代码画面、正文 2 个代码块，BV1aWan6FEn9 只保留 1 帧 YAML 前置元数据，正文不再输出噪声代码块。剩余问题是 OCR 符号错误、模型偶尔省略代码块、个别代码块偏短，需要多帧合并和代码清理。
4. **ASR 的 GPU 路径已经打通，不再只能抠 CPU。** GPU `large-v3` 从 260s 降到 65s（4x），GPU `large-v3-turbo` 降到 15.5s（16.8x），完整 6 分钟视频流水线约 98s。turbo 的字符相似度 97.1%，产品名需要 native hotwords 才能稳定，因此默认仍保留 `large-v3`，turbo 作为速度选项。
5. **图片体积有了可调参数。** 10 分钟、26 张图对应 1.2 MB 的单文件 HTML；现在可以用 `render.image_width` / `render.image_quality` 压到 900 KB 以下。对网页分享来说还能接受，但还缺默认压缩策略或响应式尺寸。
6. **旧任务的 LLM 用量缺失。** `job.json` 里 `usage` 为 0，但 write 阶段确实跑了 27s；这是早期版本没有记录用量，不是这次评测算错。评测会把它标成提示，不参与警告。

## 下一步

按收益排序：

1. 代码保真继续打磨：同一画面的多帧 OCR 合并、去掉 heredoc 外层命令、按语言清理符号和语言标注；模型漏写代码时保留兜底。
2. ASR 性能：GPU 已落地（`large-v3` 4x、turbo 16.8x），turbo 暂不默认；下一步用更多中文技术视频验证 turbo 的术语/细节损失，再决定是否按 GPU 自动选 turbo，并对比云端 ASR 的成本和稳定性。
3. 图片默认压缩策略：评估 WebP 质量 / 响应式尺寸的默认组合，在清晰度和文件体积间取平衡。
4. 写作时优先引用已有配图；如果某节有图但正文完全不引用，自动重写或裁掉。
