## 发现

1. **时间戳和章节结构是稳的。** 两条都 0 错误、100% 覆盖、没有空节/短节/长节。这说明“模型只给句子编号、代码换算时间”的设计有效，后续优化不要动这条底线。
2. **配图有 19%–24% 没进正文，但还没到失控。** 26 张里 5 张、17 张里 4 张没被引用；`v2doc eval` 只在闲置比例超过 30%，或某一节有图却一张都没用时告警。真正要盯的是“某节有图但正文完全不引用”，而不是强迫模型把每张图都塞进去。
3. **代码画面没有变成代码块。** Obsidian 的 Dataview / Tasks 语法、浏览器视频里的 Node.js 片段都被 OCR 读到了，但正文 0 个代码块。这是当前成稿最明显的保真缺口，也是 `使用手册` 里已经承认的限制。两条基线在 `v2doc eval` 里都只剩这一条警告。
4. **速度瓶颈不在写作。** ASR 占 67%–71%，OCR 占 19%–23%，LLM 写作只占 5%。所以“并行写作”不是第一优先级；先把 Whisper 批量推理、OCR 并行/抽帧筛选做好，收益更大。
5. **图片体积偏大。** 10 分钟、26 张图对应 1.2 MB 的单文件 HTML。对网页分享来说还能接受，但还有压缩空间（WebP / 质量参数 / 响应式尺寸）。
6. **旧任务的 LLM 用量缺失。** `job.json` 里 `usage` 为 0，但 write 阶段确实跑了 27s；这是早期版本没有记录用量，不是这次评测算错。评测会把它标成提示，不参与警告。

## 下一步

按收益排序：

1. 写作提示词 + 后处理支持代码块：同一画面的多帧 OCR 合并、保留缩进、标注语言；质检查“有代码画面但没代码块”，并把这类问题纳入定向重写。
2. ASR 批处理 + OCR 并行，目标是把 10 分钟视频的总耗时压到 5 分钟以内。
3. 图片转 WebP / 降低内嵌质量，控制单文件 HTML 体积。
4. 写作时优先引用已有配图；如果某节有图但正文完全不引用，自动重写或裁掉。
