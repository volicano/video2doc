### 代码保真修复后的复测

2026-10-23 对 BV1XKJR6xE5e 从 write 阶段重跑（`v2doc resume output/BV1XKJR6xE5e --from write`），只改写作输入与后处理，不动 ASR / OCR：

| 未引用配图 | 4 | 4 |
| HTML 体积 | 1.2 MB | 897 KB |
| write 阶段耗时 | 19.1s | 14.4s |

修复做了三件事：

1. 画面 OCR 不再一律压成一行：代码画面保留换行，并标成 `【代码画面】`；
2. 抽帧给代码画面保留名额，避免低分的代码截图被高分 UI 截图挤掉；
3. 写作提示要求输出围栏代码块；如果模型只写免责声明不写代码，按 OCR 里的 heredoc 抽一段代码补上。

复测里第 4 节已经能还原 `const task = await ...`、`openOrReuseTab(...)` 和 `snapshotText()`。这不代表所有代码都能还原：OCR 仍会认错符号，heredoc 外层命令可能被一起抄进代码块；下一步要做多帧合并和代码清理。

| 指标 | 串行 | 4 线程 |

中途失败时，已完成的帧会保留；重新 `--from ocr` 只补未完成的帧。成功收尾后检查点自动删除。

## 发现

1. **时间戳和章节结构是稳的。** 两条都 0 错误、100% 覆盖、没有空节/短节/长节。这说明“模型只给句子编号、代码换算时间”的设计有效，后续优化不要动这条底线。
2. **配图有 19%–24% 没进正文，但还没到失控。** 26 张里 5 张、17 张里 4 张没被引用；`v2doc eval` 只在闲置比例超过 30%，或某一节有图却一张都没用时告警。真正要盯的是“某节有图但正文完全不引用”，而不是强迫模型把每张图都塞进去。
3. **代码画面修复后能进正文了，但还不稳定。** 原基线里 Obsidian 的 Dataview / Tasks 语法、浏览器视频的 Node.js 片段都被 OCR 读到了，正文却是 0 个代码块。修复后 BV1XKJR6xE5e 复测出 2–3 个代码块，代码画面警告消失；但 OCR 符号错误、heredoc 外壳、语言标注不准仍然存在。兜底只保证「有代码块」，不保证逐字正确，所以还要继续做多帧合并和代码清理。
4. **速度瓶颈仍在 ASR。** OCR 并行后从 72s 降到 47s，但 ASR 仍占 77%（264s），LLM 写作只占 4.6%。CPU 上把 Whisper 改成 batched pipeline 只有 1.12x，收益不够；下一步要看 GPU / 云端或更小模型，而不是继续抠写作。
5. **图片体积偏大。** 10 分钟、26 张图对应 1.2 MB 的单文件 HTML。对网页分享来说还能接受，但还有压缩空间（WebP / 质量参数 / 响应式尺寸）。
6. **旧任务的 LLM 用量缺失。** `job.json` 里 `usage` 为 0，但 write 阶段确实跑了 27s；这是早期版本没有记录用量，不是这次评测算错。评测会把它标成提示，不参与警告。

## 下一步

按收益排序：

1. 代码保真继续打磨：同一画面的多帧 OCR 合并、去掉 heredoc 外壳、按语言清理符号；把「有代码画面但没代码块」纳入自动重写。
2. ASR 性能：CPU 上 batched pipeline 只有 1.12x，暂不默认；优先验证 GPU / 云端，或用更小模型配合术语表，目标把 10 分钟视频压到 5 分钟以内。
3. 图片转 WebP / 降低内嵌质量，控制单文件 HTML 体积。
4. 写作时优先引用已有配图；如果某节有图但正文完全不引用，自动重写或裁掉。
